## Project

Tenancey is a test and learning project. Its purpose is to work out a **multi-tenant, multi-database**
Laravel setup using [stancl/tenancy](https://tenancyforlaravel.com/) v3 (v3.10.1+ supports Laravel 13).
The stack is Laravel 13 on PHP 8.4 with MySQL. **React + TypeScript comes later**, so don't add it until asked.

Phases:
1. Environment, DB access, frontend build, Node pinning: **done**.
2. Tenant bootstrapping with Blade (central admin, provisioning pipeline, tenant login): **done**.
   Design: `docs/superpowers/specs/2026-10-02-tenant-bootstrapping-design.md`.
3. React + TypeScript frontend.

## Environment

- Served by Valet at **http://tenancey.test/** (`APP_URL`). Don't use `php artisan serve` for browsing.
- MySQL `127.0.0.1:3306`, user `root`, empty password. The central (landlord) DB is **`tenancey`**.
- **The MySQL server may be shared with other projects**, which can own similarly named databases
  (e.g. `tenant_<uuid>`). This project's tenant databases are `tenancey_{uuid}`
  (`TENANT_DATABASE_PREFIX`). Never drop databases or users by pattern.
- Redis (local, phpredis) holds queues, cache and sessions. Mail goes over SMTP to HELO on port 2525.
- Central admin login: `admin@tenancey.test` / `password` (from `DatabaseSeeder`).
- Horizon runs under supervisor: `deploy/supervisor/` (README there).

## Multi-tenancy (stancl/tenancy v3, one database per tenant)

- **Two worlds.** Central routes (`routes/web.php`, names `central.*`) are bound to `CENTRAL_DOMAIN`.
  Tenant routes (`routes/tenant.php`) answer on `{subdomain}.tenancey.test`.
  - Central admins: `App\Models\CentralUser`, guard `central`, pinned to the landlord DB.
  - Tenant users: `App\Models\User`, guard `web`, in the tenant DB, with spatie roles.
- **Tenant identity.** `id` is the int auto-increment primary key, used internally and in job
  payloads. `uuid` is stancl's **tenant key**: `tenancy()->find()`, `tenants:* --tenants=`, queue
  payloads, resource names, admin URLs.
- **No `domains` table.** One tenant, one `subdomain` column.
  `App\Tenancy\SubdomainTenantResolver` is bound in place of stancl's DomainTenantResolver.
- **`enabled` vs `state`.**
  - `enabled` (bool) is the admin's on/off switch.
  - `state` (`App\Enums\TenantState`, int, with `describe()`) is the lifecycle: Provisioning,
    Ready, Failed, Deleting, Deleted.
  - Open to users only when `isAccessible()`, i.e. enabled AND Ready.
- **Deleting.** The teardown chain drops resources, then sets state Deleted and **soft deletes** the
  row, which is the record. Its subdomain stays reserved forever. `Tenant::$dispatchesEvents` maps
  stancl's TenantDeleted to `forceDeleted` only, so a soft delete fires no stancl delete handling.
- **DB credentials.** Optional dedicated database user per tenant (create form checkbox).
  - Without one, `db_username`/`db_password` are null and the tenant connects with the master
    `.env` credentials. `App\Tenancy\TenantDatabaseConfig` drops the nulls, otherwise stancl
    would connect as username NULL.
  - With one, empty fields are generated by `App\Tenancy\Database\DatabaseCredentials`:
    - Username: `TENANT_DB_USER_PREFIX` (empty in production) plus random lowercase letters and
      digits, 16 characters in total.
    - Password: 12–24 characters.
  - A typed username must match `TenantResourceGuard::USERNAME_PATTERN`, must not be reserved
    (root, the master user, ...), must not be used by any tenant, and **must not already exist
    on the database server**.
  - `db_password` uses the `App\Casts\TenantSecret` cast: `TENANT_DB_KEY`, falling back to
    `APP_KEY`. Rotating `TENANT_DB_KEY` means re-encrypting every `db_password`.
  - `db_master_access` is **recorded only**. The app never grants or revokes anything on the
    master `.env` user.
  - `db_user_created_at` proves provisioning created the user. Retry recreates and teardown
    drops a user ONLY when it is set. A same-named user we did not create stops provisioning
    and is never dropped.
- **Database users go through `App\Tenancy\Database\DatabaseUserManager`.**
  - Resolved per driver from `tenancy.database.user_managers`: MySQL/MariaDB today, add a pgsql
    class for Postgres.
  - Implementations quote every value, because usernames and passwords can be typed in.
  - **Never use stancl's `PermissionControlledMySQLDatabaseManager`.** It interpolates the
    password into SQL. Its `createDatabase()` also runs CREATE USER, which with no username
    created MySQL's anonymous `''@'%'` user: passwordless, with ALL on the tenant DB (it
    happened, 2026-10-02). `config/tenancy.php` `managers` stays the plain `MySQLDatabaseManager`.
- **Provisioning** is `App\Services\TenantProvisioner`: it saves the row, then dispatches a
  `Bus::chain` of `App\Jobs\Provisioning\*` on the `provisioning` connection. Stancl's own
  TenantCreated/Deleted pipelines are switched off. **Teardown** is `App\Services\TenantTeardown`
  plus `App\Jobs\Teardown\*`.
- **Rules for tenant jobs** (`App\Jobs\TenantJob`):
  - Take only the tenant `id` and reload the row.
  - Be idempotent; Retry re-runs the whole chain.
  - Never leave tenancy initialized: `handle()` ends it in `finally`. Stancl v3 does not end it when
    tenant code throws, and a Horizon worker would then run its next job in that tenant.
- **Resource guard.** `App\Tenancy\TenantResourceGuard` compares EXACT expected names (prefix plus
  uuid/id), not just prefixes: `tenancey_testing` also starts with `tenancey_`. Keep it in front of
  every DDL and storage deletion.
- **Roles.** spatie/laravel-permission tables live in each tenant DB.
  - `TenantDatabaseSeeder` creates `admin` and `member`; the first user gets `admin`.
  - `App\Tenancy\SpatiePermissionsBootstrapper` gives each tenant its own permission cache key and
    clears the registrar's in-memory collection on every switch.
  - The seeder runs once per tenant: new roles or permissions for existing tenants need a backfill
    tenant migration.
- **Queues.** All queues are on the unprefixed Redis `queue` connection.
  - Connections: `redis` is tenant-aware; `central` and `provisioning` set `central => true`.
  - Every Horizon supervisor `timeout` must stay below its connection's `retry_after`, and
    supervisor's `stopwaitsecs` must stay above the longest timeout.
- **Logging.** Provisioning, teardown and the audit trail go to the daily `tenancy` channel,
  `storage/logs/tenancy-*.log`.
  - `TenantJob::handle()` logs each step's start, finish (with `duration_ms`), skip (`skip()`)
    or failure (with the exception).
  - Laravel `Context` tags every line with `tenant_uuid`, `tenancy_run` (one per
    provision/retry/teardown run) and `tenancy_step`. It travels with the queued chain.
  - Read it at `/log-viewer` (opcodesio/log-viewer). That is central domain only, behind
    `auth:central`, and log files cannot be deleted from it. A tenant's page links to it
    searched by uuid.
  - Never log secrets: passwords and tokens.
- **Audit log** (`App\Models\AuditLog`, central `audit_logs`, append-only).
  - Records central sign-in, failed sign-in and sign-out, and tenant create, rename,
    enable/disable, retry and delete.
  - Records every impersonation step, refusals included.
  - `AuditLog::record()` also writes the entry to the `tenancy` channel.
  - UI at `/audit`; the last 10 entries show on each tenant's page.
- **Impersonation** (`App\Services\Impersonation`; not stancl's UserImpersonation).
  - A central admin enters an enabled, Ready tenant as its **first admin**: the lowest-id user
    with the `admin` role.
  - Link: a one-time token valid 60s, stored only as a SHA-256 hash in `impersonation_tokens`,
    claimed with one atomic UPDATE.
  - Session: the `impersonator` session key, a red banner, and a 60-minute limit
    (`IMPERSONATION_SESSION_MINUTES`).
  - While impersonating, the forced password change is skipped and the password page is
    blocked.
  - End (or log out, or the session expiring) returns to the central tenant page.
  - Old tokens are pruned by the scheduled `model:prune`, which needs `schedule:run`.
- **Links in queued or central code:** use `$tenant->url()`, never `url()`.
- **Cache isolation comes from the per-tenant Redis prefix.** A non-Redis cache store is shared by
  all tenants.
- **Tenant migrations** live in `database/migrations/tenant`. Changing an already-run migration
  never reaches existing tenants: add a new file.
- **`CentralUser` vs `User` is deliberate**. Don't use the `web` guard on
  central routes: with no tenant initialized, `App\Models\User` would read the landlord `users` table.
- **Resetting the landlord DB.** Delete tenants through the UI first, so their databases, storage
  and keys go with them. `migrate:fresh` alone orphans every tenant's resources.

## Frontend / Node

- Node **22.12.0** is pinned in `.nvmrc`. A `chpwd` hook in `~/.zshrc` auto-switches on `cd`, and the
  system default stays 20.19.4. In a non-interactive shell, run `source ~/.nvm/nvm.sh && nvm use` first.
- `npm run dev` does a **one-shot** development build (unminified) into `public/build`, then exits.
  The app keeps working with no process running.
- `npm run watch` rebuilds on change. `npm run hot` starts the Vite HMR server. `npm run build`
  makes the minified production build.
- `composer dev` / `php artisan dev` runs the server, Horizon, logs and `npm run hot` (the vite
  entry is overridden in `AppServiceProvider`).
- If pages try to load assets from `localhost:517x`, a stale `public/hot` file is the cause: an HMR
  server was killed uncleanly. Delete it.

## Testing

- Tests use real MySQL (`tenancey_testing`) and test-only prefixes: `tenanceytest_`, `tx_`,
  `storage/testtenant_`, and Redis DBs 13–15. All of these are set in `phpunit.xml`.
- `Tests\TestCase` refuses any other database. It uses `DatabaseTruncation` (not `RefreshDatabase`,
  because `CREATE DATABASE` commits the open transaction). It runs the `provisioning` connection
  synchronously, and cleans up test-prefixed tenant resources before and after each test.
- `$this->createTenant('acme')` provisions through the real chain. Add `dedicatedDatabaseUser: true`
  for the own-database-user path. Typed test usernames must start with `tx_` so cleanup finds them.
- The `tenancy` log channel is muted in tests (`null`), so runs never touch the real log.
  `TenancyLoggingTest` points it at its own file.
- `actingAs($admin, 'central')` switches the default guard. Call `auth()->shouldUse('web')`
  before tenant-domain requests in the same test. `$this->tenant('acme')` re-reads it by subdomain, trashed included. After a request to a tenant URL,
  call `tenancy()->end()` before acting centrally in the same test.
